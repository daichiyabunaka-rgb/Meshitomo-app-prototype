# 趣味特化型マッチングアプリ 要件定義書・基本仕様書

**バージョン**: v1.0（ドラフト）
**対象スコープ**: 第1弾「飯とも」v1 / v1.5（ビジネスユーザー）
**作成日**: 2026年2月
**ステータス**: 要件確定待ち（法務レビュー項目あり）

---

## 1. 概要

### 1.1 目的

同じ趣味（第1弾は「食事」）を持つ近隣ユーザー同士を、**顔ではなく趣味・中身ベース**でマッチングし、以下を実現する。

1. 一般ユーザー同士：今から・近くで、飯友達を探して食事に行く
2. ビジネスユーザー：AI接客・地図連携で、近隣のユーザーに店舗を知ってもらい来店へつなげる
3. コミュニティ：常連・同じ趣味の人同士のグループ、イベント企画

### 1.2 コンセプト上の設計原則

| 原則 | 内容 |
|---|---|
| 顔画像禁止 | プロフィール画像は「趣味に関連する画像のみ」許可（料理写真、店内写真、バイク、犬など）。本人の顔が写った画像はアップロード不可（モデレーションで拒否・削除） |
| 恋愛目的禁止 | 利用規約で「恋愛・異性交際目的の利用」を明示的に禁止。違反は BAN 対象 |
| 時限性 | 募集は期限付き（1〜3時間）。期限が来たら自動消滅。「今から」感が出会い系化を防ぐ |
| 距離の粗表示 | 正確な位置は非公開。「〜1km / 1〜3km」のような大ざっぱな距離のみ表示 |

### 1.3 前提と未確定事項（法務レビュー必須）

| 項目 | v1 の対応 | 備考 |
|---|---|---|
| 出会い系サイト規制法 | サービスの実質を「趣味仲間探し」とし、規約・モデレーションで異性交際目的利用を排除 | 弁護士による非該当性確認を必須とする。これが本プロジェクト最大のブロッカー |
| 未成年利用 | **v1 は18歳以上のみとする** | 「18歳以下も使用可」は酒類提供店舗を含む設計上リスクが高いため、法務確認の上 v2 以降で検討 |
| 酒類関連の勧誘 | 20歳未満（18・19歳）のユーザーには酒類関連の店舗案内・募集を一切非表示 | v1 で18歳以上限定にしても20歳未満が含まれるため、年齢フィルタは必須機能 |
| 風営法対象店舗 | ビジネスユーザー登録時に業態審査。接待を伴う業態は v1 では受付不可 | 審査フロー・審査基準の整備が必要 |
| 迷惑防止条例（客引き） | ビジネスユーザーの営業 ・AI接客はアプリ内完結とし、押しつけのない設計（一斉配信はしない）。オプトアウト手段を常時提供 | 個別自治体への確認は開発中に実施 |
| 個人情報保護法 | 位置情報・嗜好データの第三者提供は「匿名加工統計」に限定 | 店舗ダッシュボードには集計値のみ表示 |
| 景品表示法等 | 店舗情報・AI応答の誇大禁止、健康効能に関する言及禁止 | 店舗投稿物の審査ガイドラインを整備 |

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| 一般ユーザー | 無料で利用する個人。飯ともを探す側 |
| ビジネスユーザー | 有料プランで登録する店舗・事業者・個人営業主 |
| 募集（Recruitment） | ユーザーが近隣に向けて時限で発信する「参加者募集」。投稿から1/2/3時間後に自動消滅 |
| 応募（Application） | 募集への参加申請。主催者が承認するとグループチャットが生成される |
| コミュニティ | 常設のグループ。誰でも作成可、参加自由（承認制も選択可） |
| イベント | コミュニティまたは個人が企画する日程付きの集まり |

## 3. スコープとリリース計画

| フェーズ | 内容 | 目的 |
|---|---|---|
| **v1** | 会員登録 / プロフィール（趣味） / 近くの人 / 募集・応募 / グループチャット / 飯ともカテゴリのみ / 通報・モデレーション | コア価値（今から近くで飯とも）の検証 |
| **v1.5** | ビジネスユーザー（店舗）登録 / 店舗ページ / AI接客（有料）/ 地図連携（アプリ内マップ + Googleマップ）/ 課金 | 収益化開始 |

v1 で実装するのは 5.1〜5.4（会員登録／近くの人・募集／交流／プロフィール）まで。5.5 以降は v1.5 以降の機能だが、データモデルは v1.5/v2 を見据えて定義する。

## 4. ペルソナ

### 一般ユーザー
- 20代〜50代、一人暮らし、転職・引っ越しが多い
- 「今夜一人で飯に行くのが寂しい」「行きたい店はあるが誘う相手がいない」
- 恋愛マッチングアプリには抵抗がある（恋愛目的でない人）

### ビジネスユーザー
- 飲食店オーナー（居酒屋、ラーメン、カフェ、スイーツ等）
- 「雨天・閑散時間に来店を増やしたい。AI接客で問い合わせ対応と、地図から来店への導線を強化したい」
- 月額数千円〜1万円程度の予算感で、新規客よりも「2人以上での来店」を増やしたい

## 5. 機能要件

### 5.1 会員登録・認証

| 要件 | 内容 |
|---|---|
| FR-1-1 | SNS 認証（Apple / Google / LINE）。v1 では電話番号認証を必須としないが、通報対策としてアカウント単位のレート制限を実装 |
| FR-1-2 | 登録時の必須入力：ニックネーム、年代（10歳刻み表示、生年非公開）、性別（非公開も選択可）、居住エリア（市区町村レベル）、興味カテゴリ（複数選択：居酒屋/焼肉/ラーメン/カフェ/スイーツ/激辛/エスニック等 20〜30種）、好きな食べ物・飲食シーンの自由記述（140字） |
| FR-1-3 | **アイコンは写真アップロードまたは提供アイコンセットからの選択**。アップロード画像は AI による顔検出で自動審査し、顔が検出された場合は拒否 |
| FR-1-4 | 年齢確認：生年月日を入力させる（18歳以上チェック用）が、プロフィールには公開しない |
| FR-1-5 | 退会：アカウント削除時のデータ保持期間（アクティブデータ即時削除、バックアップ90日）を規約に明記 |

### 5.2 近くの人・募集（コア機能）

| 要件 | 内容 |
|---|---|
| FR-2-1 | 「募集をかける」：以下を指定して募集を発信できる |
| | - ジャンル（今から飲みに行く / 飯 / カフェ 等） |
| | - タイトル・本文（例：「今夜19時から新宿で焼肉！ひとり参加歓迎、先着2人」） |
| | - 条件設定：性別指定（任意）、人数上限、ひとり参加歓迎の明示 |
| | - 有効期限（1 / 2 / 3 時間、期限切れで自動消滅） |
| | - 待ち合わせ場所：駅名・店名（自由記述、地図ピンは任意） |
| FR-2-2 | 「近くの人」リスト：現在地から粗い距離（〜1km / 1〜3km / 3〜5km / 5〜10km）で、近くのアクティブな募集・ユーザーを一覧表示。並び替え：距離×新着 |
| FR-2-3 | ユーザーの稼働状態（オンライン / 募集受付中 / オフライン）を表示。オフラインのユーザーは一覧に出ない（意図しない接触の防止） |
| FR-2-4 | 検索：ジャンル、キーワード、距離でフィルタ可能 |
| FR-2-5 | 募集は同一ユーザーが同時に1件まで（スパム防止） |

### 5.3 応募・交流

| 要件 | 内容 |
|---|---|
| FR-3-1 | 応募：募集詳細から「参加したい」ボタンで応募。一声メッセージ（任意、140字） |
| FR-3-2 | 主催者は応募一覧から承認／却下。承認人数が上限に達したら募集は自動的に締切 |
| FR-3-3 | 承認されたメンバーでグループチャットが自動生成。参加者はその後も辞退可能 |
| FR-3-4 | 1:1 のダイレクトメッセージも可能とするが、募集への応募経由でのみ送れる設計とする（いきなり DM される対策）。v1 はグループチャット中心 |
| FR-3-5 | メッセージ：テキスト、絵文字スタンプ。画像投稿は v1 では不可（モデレーションコストを抑えるため、v2 で検討） |

### 5.4 プロフィール・中身重視設計

| 要件 | 内容 |
|---|---|
| FR-4-1 | 趣味・嗜好の表現をリッチにする（好きな食べ物、辛さレベル、ひとり飯 OK/NG、店員さんと話すのが好き 等）を「飯ともステータス」としてマイページに表示 |
| FR-4-2 | 過去の参加募集数、参加者からの評価（「一緒に飯に行きやすい」ボタン式、v1.5 実装）を表示 |
| FR-4-3 | ブロック／通報：非表示、通報（理由入力）。通報数が閾値を超えたら自動アカウント凍結 → 人力審査 |

### 5.5 ビジネスユーザー（v1.5）

| 要件 | 内容 |
|---|---|
| FR-5-1 | 店舗登録：店舗名、業態（審査対象）、住所、営業時間、座席数、写真（料理・店内のみ。顔写真禁止は一般ユーザーと同じ基準） |
| FR-5-2 | 業態入力に「酒類提供の有無」を必須化。酒類を提供する店舗の案内・AI接客案内は20歳未満のユーザーへ非表示 |
| FR-5-3 | **AI接客（有料機能）**: ビジネスユーザーは店舗情報を登録するだけで、AI（LLM）が来店前の質問対応・案内を行う。雨天・閑散時間など状況に応じた応答、常連への挨拶文作成支援を含む。応答ログは店舗ダッシュボードで確認できる |
| FR-5-4 | **地図連携**: 近くの店舗をアプリ内マップ（OpenStreetMap タイル、APIキー不要）にピン表示。各店舗は「Googleマップで開く」（標準URL。本開発では Google Maps SDK に移行し、アプリ内で経路案内まで表示） |
| FR-5-5 | 効果測定: AI接客の応答数・来店導線・閑散時間のアクセス推移を店舗ダッシュボードに表示 |
| FR-5-6 | 課金：月額制（ライト／スタンダード／プレミアム）。決済は Stripe / RevenueCat 等の標準的な手段を利用 |

### 5.6 コミュニティ（v2 で詳細化、v1 は最小実装）

| 要件 | 内容 |
|---|---|
| FR-6-1 | コミュニティ作成：誰でも可（名前、説明、カテゴリ、公開／承認制、地域） |
| FR-6-2 | イベント：コミュニティに紐付けて日程・店・募集人数を設定し、参加受付 |
| FR-6-3 | ビジネスユーザーも一般ユーザーも同じコミュニティに参加可 |

## 6. 非機能要件

| 項目 | 要件 |
|---|---|
| プラットフォーム | iOS / Android（クロスプラットフォーム：Flutter または React Native）。Web 管理画面（モデレーション用） |
| 位置情報プライバシー | 位置情報は端末側で geohash（精度レベル5〜6程度）に変換して送信。サーバーには生の緯度経度を保持しない。退会時に即時削除 |
| セキュリティ | TLS 通信、認証トークン（短期アクセストークン＋リフレッシュトークン）、パスワードレス（SNS認証） |
| 応答性能 | 募集の一覧取得は P95 200ms 以内（キャッシュ活用）。プッシュ通知は P95 30秒以内 |
| 拡張性 | カテゴリ（飲み/犬/キャンプ等）はマスタデータ化し、アプリ再リリースなしで追加可能 |
| モデレーション | AI 審査（顔画像検出、禁止ワード）＋人力審査ワークフロー。通報 → 凍結 → 審査の SLA 48時間 |
| アナリティクス | 登録 → 募集投稿 → 応募 → 成立（チャット生成） → 実参加（自己申告チェックイン）のファネル KPI を計測 |

## 7. データモデル（概要）

```
users (id, auth_provider, nickname, birth_year(非公開), gender, gender_public,
       city_geohash, role [general|business], status, created_at)
profiles (user_id, bio, favorite_foods_json, interests_json,
          participation_count, rating_score, icon_media_id)
media (id, owner_user_id, media_type [icon|store_photo], moderation_status)
recruitments (id, host_user_id, genre_id, title, body, capacity, expires_at,
              meetup_name, status [active|fulfilled|expired|cancelled], created_at)
applications (id, recruitment_id, applicant_user_id, message,
              status [pending|accepted|declined], created_at)
rooms (id, recruitment_id, type [group], created_at)
room_members (room_id, user_id, joined_at, left_at)
messages (id, room_id, sender_user_id, body, created_at)
communities (id, name, description, category_id, visibility, owner_user_id, created_at)
community_members (community_id, user_id, role, joined_at)
events (id, community_id, title, starts_at, location_name, capacity, status)
stores (id, business_user_id, name, industry_type, serves_alcohol,
        address, geohash, business_hours_json, created_at)
ai_concierge_logs (id, store_id, user_id, question, answer, created_at)
reports (id, reporter_user_id, target_type, target_id, reason, status, reviewed_at)
blocks (blocker_user_id, blocked_user_id, created_at)
subscription_plans (id, name, price, features_json)
subscriptions (id, store_id, plan_id, status, period_start, period_end)
```

設計メモ：
- 募集の期限切れは毎分のバッチで `status` を `expired` に更新。クライアントは `_expires_at` を見て表示制御も行う（二重防護）
- AI接客の応答ログは `ai_concierge_logs` に蓄積し、店舗ダッシュボードの効果測定に使う\r\n- 距離検索は geohash プレフィックス照合で実装し、生の緯度経度での距离計算はクライアント側で行わない

## 8. 画面フロー

```
[初回起動]
  オンボーディング（コンセプト説明 + 恋愛目的禁止の同意）
    → SNS 認証
    → プロフィール入力（ニックネーム / 年代 / 興味カテゴリ / アイコン）
    → 位置情報・通知の権限リクエスト
    → ホーム

[一般ユーザー ホーム（タブ構成）]
  1. 近く（デフォルト）
     - アクティブな募集カード（距離・残り時間・人数・ジャンルタグ・主催者の嗜好）
     - 「募集をかける」フローティングボタン
  2. 部屋（チャット一覧）
  3. 探す（カテゴリ / コミュニティ / 店舗 ※店舗はv1.5）
  4. マイページ（プロフィール編集、設定：通知 / ブロック一覧）

[募集フロー]
  募集作成 → 投稿 → 近くの人に表示
  閲覧者が「参加したい」→ 主催者に通知 → 承認 → グループチャット生成
  期限到来 → 自動消滅

[ビジネスユーザー ホーム]（v1.5）
  ダッシュボード（AI接客応答数 / 来店傾向） / 店舗ページ編集 / AI接客の設定 / 地図連携設定 / プラン管理
```

## 9. KPI

| フェーズ | KPI |
|---|---|
| 起動初期（0〜3ヶ月） | 週次アクティブユーザー（WAU）、募集投稿数/日、募集あたり応募数 |
| 定着（3〜6ヶ月） | 募集成立率（投稿→チャット生成）、成立後チェックイン率、リピート飯とも率（同一ユーザーと2回以上） |
| 収益化（6ヶ月〜） | ビジネスユーザー数、AI接客経由来店数、解約率、LTV |

初期は「募集あたり応募数」が最重要。これが1.0を下回る場合、リリース地域をさらに絞る（例：東京都心の主要駅周辺のみ）か、募集 UX を簡素化する。

## 10. カテゴリ拡張戦略

「飯とも」で成立率データが得れたら、次に拡張するカテゴリは以下の基準で選ぶ：

1. 一般ユーザーの行動頻度が高い（週1回以上）
2. ビジネスユーザー（店舗）が明確に存在し、課金対象（AI接客・地図連携）になる
3. 屋外系であれば天候の影響を受け、雨天時のビジネスユーザーの緊急性が高い

この基準でいえば、次は「飲みとも」→「車/バイク」（ガソリンスタンド、カー用品店）→「キャンプ」（アウトドアショップ）が妥当な順序。「犬とも」はビジネスユーザー（ドッグカフェ、トリミングサロン）が明確で収益性が高いが、ペットの安全確認等の固有の注意が生じるため v3 目安。
